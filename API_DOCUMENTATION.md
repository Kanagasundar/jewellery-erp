# REST API contract (CodeIgniter 4)

This is the contract the frontend's `src/repositories/api/provider.ts` already calls. The backend is **not included** — implement these
endpoints and set `VITE_APP_MODE=production` + `VITE_API_BASE_URL`.

## Conventions
* Base URL: `{VITE_API_BASE_URL}` e.g. `https://api.example.com/api/v1`. JSON in / JSON out, UTF-8, `Content-Type: application/json`.
* **Envelope** (success): `{ "success": true, "data": <payload> }` — **error:**
  ```json
  { "success": false, "error": { "code": "BUSINESS_RULE", "message": "CHN-001-0003 is already SOLD – an item cannot be sold twice", "fields": { "qty": "must be ≥ 1" } } }
  ```
  The frontend shows `error.message` to the user verbatim and maps `fields` to form errors.
* Status codes: `200/201` ok · `400` malformed · `401` not signed in (frontend returns to login) · `403` permission denied · `404` not found ·
  `409` conflict (stale/duplicate/state) · `422` validation or business-rule violation · `429` rate limited · `5xx` server (GETs are retried twice with backoff; writes are never auto-retried).
* Dates: ISO-8601 UTC strings. IDs: opaque strings. **Money: JSON numbers with ≤ 2 decimals; weights ≤ 3 decimals.** (The server must compute with DECIMAL/bcmath and round half-up; the client only previews.)
* Pagination for lists: `?limit=&offset=` (frontend currently requests `limit=10000` and paginates client-side; add server-side pagination + `q`, `from`, `to`, `status` filters before data grows large).
* **Authorization is enforced server-side per endpoint** using the permission codes in `src/domain/permissions.ts`. The frontend hides UI but is not a security boundary.
* All state-changing endpoints run in a DB transaction, write `audit_logs`, and are idempotent where noted (`Idempotency-Key` header recommended for `POST /sales`, `/payments`).

## Authentication
| Method | Path | Body → data |
|---|---|---|
| POST | `/auth/login` | `{email,password}` → `{ token?, user:{id,name,email,role} }` (prefer an HttpOnly SameSite cookie; the client sends `credentials: 'include'` and a Bearer token if present) |
| GET | `/auth/me` | → `{id,name,email,role}` or 401 |
| POST | `/auth/logout` | → `{}` |
Use short-lived access tokens + refresh, argon2id password hashes, login throttling, optional 2FA for admins.

## Read-only resources
`GET /stock-items`, `/barcodes`, `/purchases`, `/inwards`, `/stock-ledger`, `/sales`, `/sale-returns`, `/payments`, `/repairs`, `/polishing`,
`/stock-audits`, `/stock-adjustments`, `/audit-logs` (+ `/{id}`). Response shapes = the TypeScript interfaces in `src/types/entities.ts`.

## Commands (business workflows)
Each is a single transaction; on any failure nothing is persisted.

### Purchases
* `POST /purchases` / `PUT /purchases/{id}` — body `PurchaseInput` (`supplierId, invoiceNo, date, expectedDate?, notes?, lines[{productId, qty, grossWeight, stoneWeight, purityId, stoneDetails, rate, makingCharge, wastagePercent, gstPercent}], submit`). Server computes line/PO totals. Only `draft|pending` editable. `submit:true` → `pending`.
* `POST /purchases/{id}/submit` · `POST /purchases/{id}/cancel {reason}` (422 if any qty received or payments exist). `purchases.manage`.

### Stock inward
* `POST /inwards`, `PUT /inwards/{id}` — `InwardInput` (`purchaseOrderId, date, notes, items[]` one per piece). Creates/edits a **draft**; **no stock effect**. `inward.manage`. 422 if pieces exceed PO pending qty.
* `POST /inwards/{id}/submit` → `pending_approval`.
* `POST /inwards/{id}/approve` — **the only call that creates stock**: per accepted piece insert `stock_items` (status `available`, or `damaged`), a unique `barcodes` row, a `stock_ledger` row; update `received_qty`; set PO status (`partially_received|received|completed`). `inward.approve`.
* `POST /inwards/{id}/reject {reason}` · `DELETE /inwards/{id}` (draft only).

### Barcodes / inventory
* `GET /barcodes/lookup?code=` → `{ item, product, barcode }` or 404 (accepts barcode or item code; voided codes resolve to the current item).
* `POST /barcodes/printed {itemIds[]}` (print counter) · `POST /stock-items/{id}/barcode/regenerate {reason}` (voids old, issues new).
* `POST /stock-items/{id}/reserve {customerId,note}` · `/release` · `/damage {reason}` · `/restock {reason}` (each writes a ledger row).
* `GET /stock/reconcile` → `LedgerCheck` (see TS interface) — must be `ok:true` at all times.

### Branches & stock transfers
* Branches live in `settings.branches` (`GET/PUT /settings`; production: a `branches` resource). Removing a branch that holds stock → 422.
* `POST /inwards` / `PUT` take `branchId` (receiving branch). `POST /sales` takes `branchId`; every item must be held at that branch (422 otherwise). `POST /stock-audits` takes `branchId`.
* `POST /transfers {fromBranchId,toBranchId,itemIds[],note?}` (`transfers.manage`) — dispatch: items must be `available` at the source; they become `in_transit` (ledger out at source).
* `POST /transfers/{id}/receive` — items become `available` at the destination (ledger in; `branchId` changes). `POST /transfers/{id}/cancel {reason}` — only while in transit; items return to the source.
* `GET /stock/reconcile` additionally returns `branchBalances[]`.

### Sales
* `POST /sales` — `SaleInput {customerId|null, walkInName?, walkInPhone?, items[{stockItemId, discount?}], payments[{mode,amount,reference?}], advanceAdjust?, notes?, date?}`.
  Server: lock items `FOR UPDATE`, require `available`, **recompute pricing authoritatively** from product formula + metal rate in force, snapshot rate on each line, mark items `sold` + ledger, create payments + allocations, consume advance FIFO. Walk-in must pay in full. → `Sale`.
* `POST /sales/{id}/cancel {reason}` (`sales.cancel`) — status `cancelled`, items back to `available` (ledger), cash refunds posted as `refund` payments; advance-funded amounts return to the advance pool. 422 if items were already returned.
* `POST /sales/{id}/returns {itemIds[], reason, refundMode}` (`sales.return`) → `SaleReturn`; items → `returned` (need `restock`).

### Payments
`POST /payments` — `{direction, partyType, partyId, mode, amount, kind, allocations?[{docType,docId,amount}], autoAllocate?, reference?, notes?, date?}`. Validates each allocation ≤ document outstanding and Σalloc ≤ amount; unallocated remainder = advance. `payments.manage`.

### Repairs (`repairs.*`)
`POST /repairs` (`RepairInput`, optional `advance{amount,mode}` and `stockItemId` for shop-owned items) · `POST /repairs/{id}/assign {artisanId}` · `/start` · `/complete {labourFinal,note}` (artisans only on **their own** jobs — server checks `artisan_id = me`) · `/deliver` (422 unless paid in full) · `/cancel {reason}`.

### Polishing (`polishing.*`)
`POST /polishing` (item must be `available` → `polishing` + ledger) · `/{id}/assign` · `/start` · `/submit-qc {afterWeight, remarks}` (≤ before weight) · `/qc {passed, remarks}` (fail → back to in_progress) · `/return` (item → `available` with new weight, ledger).

### Stock audits
`POST /stock-audits {title, categoryId?}` · `POST /stock-audits/{id}/scans {barcode, physicalWeight?}` → `{audit, result:'matched|extra|unknown|duplicate'}` · `DELETE /stock-audits/{id}/scans/{barcode}` · `/submit` (computes discrepancies) · `/approve {note}` (`audit.approve`, posts `stock_adjustments` + ledger) · `/reject {note}`.

### Settings
`GET /settings` · `PUT /settings` (`settings.manage`).

## Reports
The demo computes reports client-side from the list endpoints. For production data volumes add server-side report endpoints
(`GET /reports/{key}?from=&to=` returning `{columns, rows}` identical to `features/reports/definitions.ts`) and swap the data source in `ReportsPage`.

## Security checklist for the backend
CORS allow-list only the Pages origin · HTTPS only · parameterised queries (CI4 Query Builder) · output encoding · per-route permission filter ·
rate limiting on `/auth/login` · request size limits · image upload validation (type, size, re-encode) · no secrets in the frontend bundle ·
`audit_logs` for every command · DB user without UPDATE/DELETE on `stock_ledger`/`audit_logs`.
